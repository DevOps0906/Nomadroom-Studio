# ADR-0003 카테고리형 제작 렌더 워커 위치·파일 전달·작업 종류

- 상태: 승인
- 날짜: 2026-11-18

| 항목 | 내용 |
|---|---|
| 맥락 | 카테고리형 쇼츠 제작(`01_PRD.md#3` P0·P1)은 원본 준비·시트·음성·합성·인코딩이 필요하다. 영상 파일은 크고 제3자 저작물일 수 있다. ADR-0001(수집 워커)의 경계를 이 기능에도 적용할지, 파일은 어떻게 주고받을지 정해야 한다. |
| 선택 | 1) 렌더는 **운영자 PC 로컬 워커**(ADR-0001 방식): FastAPI `/worker/v1/*`만 폴링·전송, DB·Supabase 키 없음, 인바운드 포트 없음. 2) 파일은 API가 발급한 **Supabase Storage 서명 URL**로만 주고받는다(비공개 버킷, 작업·파일 단위 한정, 짧은 만료 — 값 `04_API.md#제작-api`). 3) 워커 작업 종류 `prepare`(구간 추출·analysis·시트)와 `render`(음성·합성·리포트). 수집 워커와 같은 토큰·폴링 모델, 번호는 W-05부터. 4) 웹·API는 작업 ID·자산 ID만 주고받고, 워커는 작업 폴더 안에서만 파일명을 정한다(`01_PRD.md#8` 경로 주입). 5) 렌더는 (작업, 리비전, 언어)마다 하나만 진행(멱등 키). |
| 대안 | A) 클라우드 렌더(서버·컨테이너에서 ffmpeg): PC 의존 없음. 그러나 영상 처리 비용·저장·실행 시간 부담, yt-dlp 다운로드 IP 차단·약관 위험, 배포본 분석상 로컬 환경 기준 도구라 이전 비용 큼 → 이번 범위에서 기각. B) 워커가 Supabase에 직접 접속·업로드: service_role 또는 넓은 DB·Storage 권한이 PC에 퍼짐(ADR-0001 C안과 동일) → 기각. C) 공개 URL·공개 버킷 전달: 링크 유출 시 비공개 영상 노출 → 기각. D) 파일 본문을 API가 중계: API 대역폭·메모리·타임아웃 부담 → 기각. E) `prepare`·`render`를 한 작업으로 합침: 편집안 검토 단계 사이에 사람 승인이 있어 분리 필요 → 기각. |
| 결과 | 얻는 것: 워커 권한 최소(토큰+서명 URL만), 로그인·쿠키 없는 로컬 처리, 기존 워커 패턴 재사용, 단계별 재시도. 잃는 것: PC가 꺼져 있으면 준비·렌더 불가, 서명 URL 만료·재발급 처리, 대용량 전송 시간. 되돌리는 비용: 중간(워커 코드가 `apps/worker` 한 곳이라 호스트 이전은 가능하나 클라우드 이전은 ffmpeg·폰트·TTS 환경 재구성 필요). 후속 확정: 파일 보관 기간(Q5). 대안 A(클라우드 렌더) 기각 사유(비용·IP 차단)는 팀장이 수용(2026-11-18), 상태 "승인". 브라우저→Storage 직접 PUT은 `02_ARCHITECTURE.md#2` 경계 예외. |
